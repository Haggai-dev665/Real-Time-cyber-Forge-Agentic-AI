[38] (Heading1) ABSTRACT
[39] (FirstParagraph) CyberForge is a web-threat analysis and user-protection research system that combines specialised analysers, contextual evidence and human-readable explanations. The original prototype coordinated eight specialist agents through a three-stage directed acyclic graph, followed by a Reporter. Its reported evaluation on 300 URLs (150 benign and 150 harmful) yielded 94.7% accuracy, 97.9% precision, 91.3% recall and a 2.0% false-positive rate, with mean end-to-end latency of 4.05 seconds. These are retained as historical prototype results, not measurements of the revised implementation. A source review dated 18 October 2026 identifies the current implementation as a Tauri 2/Rust desktop, a Node.js 24/Express backend, a FastAPI Hugging Face service, a shared Rust core, a scoped CLI and a grant-controlled stdio MCP adapter. The ML service combines supervised gradient-boosted URL classifiers, unsupervised IsolationForest scoring, externally pretrained BERT and Qwen inference, and explicit heuristic fallbacks. Current controls include consent-based collection, authenticated workspace access, device enrollment and signed commands, evidence records, and capability-aware status reporting. Memory supplies retrieval context; it does not update model weights. The current implementation requires fresh held-out evaluation and packaged/live-service acceptance before historical performance can be attributed to it.
[40] (BodyText) Keywords: agentic AI; phishing detection; multi-agent systems; threat intelligence; real-time protection; explainable security

[43] (BodyText) CyberForge est un système de recherche consacré à l’analyse des menaces web et à la protection des utilisateurs. Le prototype initial coordonnait huit agents spécialisés dans un graphe orienté acyclique en trois étapes, suivi d’un agent rapporteur. L’évaluation historique de 300 URL (150 légitimes et 150 malveillantes) rapporte une exactitude de 94,7 %, une précision de 97,9 %, un rappel de 91,3 %, un taux de faux positifs de 2,0 % et une latence moyenne de 4,05 secondes. Ces résultats ne constituent pas une nouvelle évaluation du système révisé. La revue du code du 18 octobre 2026 identifie un client Tauri 2/Rust, un backend Node.js 24/Express, un service FastAPI sur Hugging Face, un noyau Rust partagé, une interface en ligne de commande et un adaptateur MCP stdio soumis à autorisation. Le service ML associe classification supervisée, détection non supervisée d’anomalies, inférence avec BERT et Qwen préentraînés et heuristiques explicitement identifiées. La collecte dépend du consentement; les actions et les données sont soumises à des contrôles d’accès. La mémoire conserve du contexte sans réentraîner les modèles. Une nouvelle évaluation indépendante et des essais de la version installée restent nécessaires avant de généraliser les résultats historiques à cette version.

[152] (Heading1) Chapter OneINTRODUCTION
[153] (Heading2) 1.1 Background of the Study
[154] (FirstParagraph) The volume, complexity, and impact of cyber-attacks have increased steadily since the early 2000s, with the World Wide Web becoming the main attack surface for both individuals and organisations (Provos et al., 2007). As cloud services, modern browsers, and web applications continue to grow, the security boundary has shifted away from traditional network firewalls to the user’s browser. In this environment, threats such as phishing, drive-by downloads, credential theft, malicious ads, and supply-chain attacks are now very common and highly damaging (Khonji et al., 2013). Traditional signature-based security systems are no longer effective because attackers now use fast-changing domains, hidden payloads, and short-lived infrastructure to avoid detection.
[155] (BodyText) To respond to this, researchers first used machine-learning methods and later moved into deep-learning approaches. Early studies showed that machine learning could help detect malware and phishing attacks, but they also highlighted problems like noisy data, changing attack patterns, and difficulty in real-world deployment. Later research showed that deep-learning models, especially those that analyse raw URL text and character patterns, perform better than manual feature-based systems. The introduction of Transformer models improved this further by allowing systems to understand context in sequences like URLs and logs (Devlin et al., 2019). These methods have made it easier to build automated security tools for real-world use (Buczak & Guven, 2016).
[156] (BodyText) At the same time, cybersecurity systems are moving away from single-model designs to multi-component systems made of specialised agents (Yao et al., 2023). In this approach, different agents handle different tasks such as detection, extraction, analysis, and reporting. These agents work together to make better decisions than a single model could achieve alone. This idea fits well with cybersecurity work because human analysts also follow step-by-step reasoning when checking suspicious URLs, such as checking reputation, analysing page behaviour, and mapping threats to known attack patterns like MITRE ATT&CK (Strom et al., 2018).
[157] (BodyText) Another key issue is that users now operate across many devices, including desktops, mobile phones, and cloud platforms, but security systems are often not connected across these environments. This creates gaps in protection and makes it harder to maintain consistent threat awareness. Because of this, there is growing interest in systems that can share and synchronise threat intelligence across platforms, although such systems are still not common in most practical or academic tools.
[158] (BodyText) The present study, CyberForge, is developed in response to these challenges. It is a multi-platform, agent-based cybersecurity system designed to analyse URLs in real time and protect users while they browse. The system uses multiple specialised agents to handle tasks such as URL classification, domain analysis, behavioural inspection, threat-intelligence lookup, and adversary mapping. These agents work together through a coordinated workflow to produce a final security verdict.
[159] (BodyText) Historical observations are retained as contextual evidence for later analysis. This memory and retrieval mechanism is distinct from learning model parameters. Current collection and cloud processing are independently consent-gated. The original URL experiment is reported in Chapter 4; the October 2026 source revision is documented in Chapter 3 and Appendix C and has not been assigned new detection-performance figures.
[160] (Heading2) 1.2 Problem Statement
[161] (FirstParagraph) Despite the considerable academic literature on machine learning for cybersecurity, and despite the commercial maturity of products such as Endpoint Detection and Response (EDR) platforms, three persistent problems continue to limit the practical usefulness of AI-based threat detection for ordinary users and for small organisations.
[162] (BodyText) First, single-model approaches to URL and content classification are prone to high false-positive rates. Early experimental work in the present project found that a hand-tuned heuristic risk-score formula was systematically returning a “medium” risk verdict for every URL evaluated including safe sites such as google.com and github.com because of an additive baseline offset of +0.5 in the score-normalisation step. That defect illustrates a broader problem: models trained on synthetic or imbalanced data tend to inherit biases that are not detectable until deployment, and the result is a tiring volume of alerts that makes users ignore genuine threats.
[163] (BodyText) Second, the explainability gap between an AI-generated verdict and the reasoning a security analyst would use to justify that verdict is rarely closed in current tools. A single classifier might output a probability that a URL is malicious, but it cannot, on its own, list the indicators of compromise present on the page, map observed JavaScript activity to a MITRE technique, or link the domain with prior threat-intelligence reports. The analyst, or the end user, is therefore left with a number rather than a clear story.
[164] (BodyText) Third, there is no widely deployed open architecture that fans a single browser event out across a set of specialised analysers, saves the combined result, learns from prior visits, and shows the result on the user’s desktop and mobile device at the same time. Commercial Security Orchestration, Automation and Response (SOAR) platforms meet this need at the enterprise scale, but they are out of reaching both price and complexity for the academic-research and small-team settings in which this dissertation is situated.
[165] (BodyText) CyberForge addresses these problems through specialist analysis, inspectable evidence and controlled sharing of results. The original eight-agent analysis workflow remains distinguishable from the newer durable agent-run framework: the latter currently exposes URL Analyst and Device Health templates with bounded tools, while broader autonomous planning remains future work.
[166] (Heading2) 1.3 Research Questions
[167] (Heading3) 1.3.1 General Research Question
[168] (FirstParagraph) How can a multi-agent AI system, organised as a network of specialised analysers, be designed to provide real-time and explainable threat intelligence and protection for URLs and web resources across different platforms?
[169] (Heading3) 1.3.2 Specific Research Questions
[170] (p) How can the analysis of a URL be divided among different AI agents, and what is the smallest set of agents needed to make a reliable threat assessment?
[171] (p) How can URL classification, behavioural analysis, IOC extraction, MITRE ATT&CK mapping, and threat-intelligence lookup be combined into a single system that produces consistent and accurate threat assessments?
[172] (p) What method can be used to combine the results from different agents to reduce false alarms while still identifying serious threats when strong evidence is available?
[173] (p) How can historical browsing information be used to improve threat detection, identify recurring malicious activity, and strengthen user protection over time?
[174] (Heading2) 1.4 Objectives of the Study
[175] (Heading3) 1.4.1 General Objective
[176] (FirstParagraph) To design, implement, and evaluate a multi-platform AI-driven cybersecurity system that can monitor URLs encountered during web browsing in real time, detect and explain potential threats using multiple cooperating agents, and provide timely alerts and protective feedback to users while maintaining historical context and persistent threat records.
[177] (Heading3) 1.4.2 Specific Objectives
[178] (p) To design a multi-agent decision framework that can decompose URL analysis into coordinated tasks and produce reliable real-time threat assessments for user protection.
[179] (p) To develop a unified threat-detection approach that combines multiple analytical perspectives (content, behavioural signals, structural patterns, and threat intelligence) to improve detection accuracy and consistency.
[180] (p) To design a decision-aggregation mechanism that reduces false alerts while ensuring that high-confidence malicious indicators trigger immediate user warnings and protective actions.
[181] (p) To incorporate contextual threat intelligence that improves detection quality by linking current URL behaviour with known attack patterns and external threat databases.
[182] (Heading2) 1.5 Significance of the Study
[183] (FirstParagraph) The significance of this study is threefold.
[184] (BodyText) Academically, the contribution is the integration and orchestration of complementary evidence sources rather than a claim that every component is a trained AI model. The current system includes supervised URL classifiers, an unsupervised anomaly detector, pretrained language/URL models and deterministic extraction rules. Their outputs, failure states and provenance must be distinguished. Reproducibility depends on recording source revisions, dataset splits, feature definitions and model metadata, not merely publishing application code.
[185] (BodyText) The historical development study identified and removed an additive +0.5 risk-score offset. Its small calibration set is distinct from the 300-URL evaluation. Neither a model confidence value nor successful calibration of a few selected URLs establishes calibrated probability or out-of-sample performance. The revised implementation explicitly labels unavailable engines and heuristic responses.
[186] (BodyText) The system uses modular client, backend, inference and persistence services. The backend configuration supports a configured deployment origin and the ML_SERVICE_URL inference destination; the Hugging Face deployment source is ml-services/hf_space_deploy. Heroku and Appwrite remain present in project configuration, alongside MongoDB control-plane persistence. This source review does not certify current provider availability, hosting capacity or production deployment parity.
[187] (Heading2) 1.6 Scope and Limitations of the Study
[188] (FirstParagraph) The scope of this study is defined as follows.
[189] (BodyText) The scope is URL and web-context security: analysing submitted or consent-collected addresses, examining available page signals, retrieving intelligence and presenting evidence-based warnings. Supported domain-blocking actions are mediated by native permissions or approved signed device commands. A request being queued or delivered is not proof that blocking was applied.
[190] (BodyText) The study does not extend to low-level or infrastructure-level security domains. It excludes kernel-level exploitation, firmware attacks, hardware compromise, lateral movement within enterprise networks, and post-compromise persistence mechanisms that occur beyond the browser or user-interaction layer. The system is not intended to function as a full endpoint-protection suite or an enterprise intrusion-detection system.
[191] (BodyText) The analysis workspace presents available URL, page and threat-intelligence evidence. It is not a virtual-machine malware detonation environment and does not establish arbitrary binary analysis or comprehensive endpoint protection. Observation coverage depends on supported sensors, permissions, consent and service availability.
[192] (BodyText) The system relies primarily on English-language threat-intelligence sources, classification models, and explanation frameworks. This includes structured cybersecurity knowledge bases such as MITRE ATT&CK and external threat-intelligence feeds such as AlienVault OTX. As a result, performance evaluation and interpretability are focused on English-language threat contexts.
[193] (BodyText) From a deployment perspective, the system is designed for cloud-connected environments where detection, reasoning, and response components operate across distributed services. It is not optimised for fully offline, air-gapped, or strictly on-premises enterprise deployments.
[194] (BodyText) Evaluation is separated into historical detection measurements, current source-level implementation evidence and future release acceptance. The 300-URL experiment remains the only detection-performance dataset summarised here. No new commercial comparison, cross-platform benchmark, production uptime measurement or model-quality result is inferred from the current code.
[195] (Heading2) 1.7 Definition of Key Terms
[196] (p) Agent (software). A component that executes a bounded task and returns a structured result. In this system, specialist URL-analysis agents and durable user-configured agent runs are different abstractions. The available durable templates execute fixed authorised tools; they do not yet establish unrestricted LLM-selected tool use (Wooldridge, 2009).
[197] (p) Agentic AI. A class of artificial-intelligence system in which one or more specialised agents cooperate, possibly under the direction of a coordinator, to accomplish a task that none of them could complete alone (Russell & Norvig, 2020; Yao et al., 2023).
[198] (p) API Gateway. A centralised interface layer that receives client requests, enforces authentication, and routes traffic to backend services. In CyberForge, it exposes endpoints for URL submission, agent-orchestration triggers, and result retrieval.
[199] (p) Appwrite. A backend service used for selected persisted records and integrations. The current system also uses MongoDB/Mongoose for workspace-scoped devices, agent definitions and runs, findings-related workflow and audit/control-plane records; Appwrite is not the sole system of record.
[200] (p) Behavioural Analysis. A security-analysis technique that evaluates the runtime characteristics of a webpage or URLincluding network activity, script-execution patterns, cookie behaviour, and DOM manipulate onto detect suspicious or malicious activity.
[201] (p) BERT. Bidirectional Encoder Representations from Transformers a pretrained Transformer architecture for natural-language understanding (Devlin et al., 2019). In CyberForge, a domain-adapted BERT model is used to classify URL strings.
[202] (p) DAG (Directed Acyclic Graph). A graph in which edges have direction and no cycle exists. Used in this dissertation to describe the orchestrator’s stage structure, in which each stage may depend on outputs of an earlier stage.
[203] (p) DGA (Domain Generation Algorithm). A class of algorithms used by malware families to generate large numbers of pseudo-random domain names for command-and-control rendezvous (Antonakakis et al., 2012).
[204] (p) Evidence record. A stored account/workspace-scoped analytic or action record. Current findings, derived incidents and deterministic evidence reports support explicit provenance. Legacy in-process recent-report buffers are caches, not durable audit history.
[205] (p) False Negative. A system outcome in which a malicious URL or resource is incorrectly classified as safe, representing a critical security failure in threat-detection systems.
[206] (p) False Positive. A system outcome in which a safe URL or resource is incorrectly classified as malicious. Reducing false positives is a key objective of CyberForge’s aggregation strategy.
[207] (p) Heuristic Analysis. A rule-based or statistical approach to threat detection that does not rely on trained models but instead uses predefined logic such as entropy scoring, pattern matching, or domain-structure evaluation.
[208] (p) Hugging Face Spaces. The configured hosting destination for the canonical FastAPI ML service, including detector loading, inference and owner-authorised training. Service-to-service authentication and per-capability readiness are distinct from public health availability.
[209] (p) Inference Pipeline. The sequential process through which input data (such as a URL) is passed through multiple models and agents to generate a final classification or security verdict.
[210] (p) IOC (Indicator of Compromise). A piece of forensic data that suggests the presence of a security incident for example an IP address, a domain, a file hash, or a CVE identifier.
[211] (p) LLM (Large Language Model). A neural network with billions of parameters trained on large text corpora and capable of generating natural-language responses to prompts (Brown et al., 2020).
[212] (p) Memory layer. Local and backend stores that retain prior observations for retrieval and context. Optional vector-store adapters and cache code do not by themselves establish that those services are provisioned. Stored history does not constitute online learning, reinforcement learning or automatic weight updates.
[213] (p) MITRE ATT&CK. A globally accessible knowledge base of adversary tactics and techniques based on real-world observations, maintained by the MITRE Corporation (Strom et al., 2018).
[214] (p) Multi-Agent System. A distributed artificial-intelligence architecture composed of multiple specialised agents that independently process subtasks and collaboratively produce a unified output.
[215] (p) Orchestrator. In CyberForge, the back-end service responsible for dispatching agents through the three-stage DAG, aggregating their outputs, escalating verdicts, and persisting the consolidated report.

Modern attacks, including phishing, malicious redirects, and dynamically generated domains, are designed to evade static rules. This has led to a growing need for intelligent systems that can learn patterns of malicious behaviour and respond proactively rather than reactively.
[237] (BodyText) The chapter also examines how artificial intelligence and machine learning have changed the cybersecurity landscape by enabling systems to detect, classify, and respond to threats in real time. Unlike traditional approaches that depend on known threat signatures, AI-based systems can generalise from data and identify previously unseen attacks, making them more suitable for modern web environments where threats evolve continuously.

This includes systems that can block malicious URLs, generate real-time warnings, interrupt harmful sessions, and adapt their responses based on observed behaviour. In this context, AI is no longer limited to passive analysis but is increasingly embedded in protective decision-making loops that directly influence user safety.
[239] (BodyText) The review further explores URL-based and domain-generation-based detection methods, which remain central to browser-level protection systems. [246] (Heading2) 2.2 Evolution of Web Threats
[247] (FirstParagraph) The earliest body of academic work on web-based attacks concentrated on server-side vulnerabilities SQL injection, cross-site scripting (XSS), cross-site request forgery (CSRF), and remote file inclusion. Although those attack classes remain operationally significant, the center of gravity of consumer-facing web threats has shifted in the past fifteen years toward attacks that target the browser and the user directly. Provos, McNamee, Mavrommatis, Wang and Modadugu (2007), in their influential paper “The Ghost in the Browser,” documented the rise of drive-by-download attacks in which a legitimate page is silently modified to deliver an exploit chain to vulnerable browsers. Their large-scale crawl found that 1.3 % of the pages they sampled engaged in drive-by behaviour, and the authors argued presciently that the future of malicious web activity would be characterised by short-lived domains, polymorphic JavaScript, and infrastructure designed specifically to evade signature-based scanning.
[248] (BodyText) The intervening fifteen years have validated that prediction. Khonji, Iraqi and Jones (2013) provide a comprehensive literature survey of phishing detection covering more than seventy publications, observing that the most successful approaches combine lexical features of the URL, content features of the rendered page, and reputation features drawn from external feedsbut also noting that no single approach achieves both high recall and a low false-positive rate when evaluated on heterogeneous datasets. More recently, the increasing prevalence of free domain registrars (notably the .tk, .gq, .ml, .cf and .xyz zones) and the wide availability of phishing kits sold as a service have driven the cost of mounting a phishing campaign close to zero. Anderson and Roth (2018), in introducing the EMBER static-PE-malware benchmark, similarly noted that the half-life of malware family signatures has continued to shrink, making per-sample classification increasingly important relative to per-family classification.
[249] (BodyText) The implication for system design is that web-threat detection cannot rely on any single signal. A modern detector must combine string-level analysis of the URL, behavioural inspection of the page (DOM, network requests, JavaScript activity), reputation lookups in third-party feeds, and longitudinal context drawn from past observations of the same domain or actor. The eight-agent decomposition adopted by CyberForge is a direct response to this multi-signal requirement.
[250] (Heading2) 2.3 Machine Learning in Cybersecurity
[251] (Heading3) 2.3.1 Foundational scepticism
[252] (FirstParagraph) Any review of machine learning in cybersecurity must begin with the foundational critique of Sommer and Paxson (2010). Their paper, “Outside the Closed World,” argued that the success of machine learning in domains such as natural-language processing and computer vision had not at the time of writing translated to comparable success in network intrusion detection, and identified the principal reasons: the cost of misclassification asymmetry, the lack of representative ground-truth data, the high variability of legitimate network behaviour, and the difficulty of converting model output into actionable artefacts for analysts. Although the specific landscape has changed considerably in the intervening years, the structural critique remains relevant; in particular, the requirements that model output be interpretable and that systems be designed for cost-asymmetric misclassification continue to inform the design of any production deployment.
[253] (Heading3) 2.3.2 Surveys of applied machine learning
[254] (FirstParagraph) Buczak and Guven (2016) review classical machine learning for cybersecurity and describe practical concerns such as concept drift, imbalance and generalisation. These concerns motivate multi-source evidence and held-out evaluation in CyberForge. The current source contains offline fitting and decision-threshold selection; it does not implement continuous online retraining or establish calibrated probability outputs.
[255] (Heading3) 2.3.3 Deep learning and Transformers
[256] (FirstParagraph) The publication of Vaswani et al.’s “Attention Is All You Need” (2017) and the subsequent introduction of BERT (Devlin et al., 2019) shifted the deep-learning research community from convolutional and recurrent architectures toward self-attention-based Transformers. While the original BERT was trained on a general English corpus (BookCorpus plus the English Wikipedia), the pre-training-and-fine-tuning paradigm proved remarkably adaptable to specialised domains. Domain-adapted BERT variants for biomedicine (BioBERT), law (LegalBERT), source code (CodeBERT), and security applications now form a substantial sub-literature.
[257] (BodyText) URLNet (Le et al., 2018) and Transformer-based representations illustrate learning directly from URL text. CyberForge retains an externally pretrained BERT URL-classification path (elftsdmr/malware-url-detect); the active trainer does not fine-tune it. The current implementation additionally trains three HistGradientBoostingClassifier models for phishing, malware-serving URLs and web-attack payloads, plus an IsolationForest on benign examples. The dissertation contribution remains system integration and evaluation, not a claim of novel Transformer training.
[258] (Heading2) 2.4 Related Works: Phishing Detection Approaches
[259] (FirstParagraph) Phishing detection is one of the most studied problems in web security because it directly targets human users through deception rather than system exploitation. Over time, research in this area has evolved in clear stages, moving from simple rule-based systems to advanced machine learning and now to deep-learning and Transformer-based approaches. Each stage improves detection ability, but also introduces new trade-offs between accuracy, adaptability, and interpretability.
[260] (BodyText) The early stage of phishing detection was mainly based on rule-based or feature-based methods. These systems relied on manually defined indicators extracted from URLs or webpage content. Common features included URL length, the use of suspicious symbols such as “@” or “-”, IP addresses used in place of domain names, abnormal subdomain structures, and HTML elements such as hidden iframes or forms. Works such as Mohammad, Thabtah, and McCluskey (2014) show that these approaches could achieve good performance under controlled conditions. However, their main weakness was rigidity. Once attackers understood the rules being used, they easily modified their phishing URLs to bypass detection. This made rule-based systems less effective over time, especially against adaptive adversaries.
[261] (BodyText) The second stage introduced classical machine-learning models, which reduced dependence on fixed rules by learning patterns from data. Instead of hard-coded detection logic, models such as decision trees, support-vector machines, and random forests were trained on extracted URL and webpage features. Studies like Sahingoz et al. (2019) demonstrated that machine-learning models could achieve very high accuracy, with ensemble methods such as random forests performing particularly well on lexical URL features. This generation of approaches was more flexible than rule-based systems and could generalise better to unseen data. However, they still depended heavily on feature engineering, meaning their performance was limited by how well human experts could design meaningful input features. They also struggled when attackers introduced subtle changes that were not captured by existing feature sets.
[262] (BodyText) The third and more recent stage is based on deep learning, especially neural networks and Transformer architectures. In this approach, the system no longer relies on manually designed features. Instead, models learn directly from raw URL strings or tokenised representations. Transformer-based models, in particular, can capture relationships between characters and tokens in a URL, allowing them to detect patterns that are not obvious through manual analysis. This makes them more resilient to small manipulations such as character substitution or URL-obfuscation techniques commonly used in phishing attacks. However, these models are usually more computationally expensive, require more data, and are less transparent compared to traditional machine-learning models.
[263] (BodyText) Despite their advantages, deep-learning models alone are not always sufficient in practical security environments. This is because real-world systems require reliability, fallback mechanisms, and interpretability under failure conditions. As a result, many modern systems adopt hybrid designs that combine deep learning with traditional methods. This allows systems to benefit from the accuracy of neural models while still maintaining simpler heuristic or rule-based components for backup and verification.
[264] (BodyText) In line with this direction, CyberForge adopts a hybrid phishing-detection approach, consistent with the survey finding that combined detection signals outperform any single approach (Khonji et al., 2013). It combines a Transformer-based URL classifier for high-accuracy detection with a lightweight heuristic-analysis layer that can operate when the primary model is unavailable or uncertain. This design improves system resilience and ensures continuous operation even under service degradation. It also reflects a broader trend in cybersecurity research, where robustness and operational reliability are considered just as important as raw classification accuracy.
[265] (Heading2) 2.5 Domain Generation Algorithms (DGA)
[266] (FirstParagraph) Domain Generation Algorithms (DGAs) are techniques used by malware to automatically create large numbers of domain names. These domains are often used for command-and-control communication, making it difficult for defenders to block them using simple blacklists. Research in this area has developed over time, moving from statistical analysis to machine learning and more recently to deep-learning approaches.
[267] (BodyText) The early and most influential work in this area is by Antonakakis et al. (2012). Their study showed that DGA-generated domains are very different from normal human-generated domain names. They tend to look random and do not follow natural language patterns. For example, they often have high character randomness (high entropy), very few vowels, unusual consonant combinations, and frequent mixing of numbers and letters. The study also showed that detecting a single malicious domain is not enough. Instead, it is more effective to detect groups of domains generated by the same algorithm, since malware families usually produce many related domains over time. This idea became the foundation for many later DGA-detection systems.
[268] (BodyText) After this, researchers started using machine-learning methods to improve detection accuracy. Instead of relying only on statistical rules, models were trained on examples of both normal and DGA-generated domains. Some studies showed that character-based neural networks could learn patterns directly from domain names and perform better than traditional statistical approaches. Later work also explored deep-learning models, including convolutional networks and Transformer-based models, which can capture deeper relationships in character sequences and improve detection of more advanced DGAs.
[269] (BodyText) However, in real-world systems, DGA detection is not only about accuracy but also about reliability and integration. Deep-learning models can be powerful, but they are often harder to deploy, depend on external services, or require heavy computation. Because of this, many practical systems still rely on simpler but stable statistical or heuristic methods, especially when working in real-time environments.
[270] (BodyText) In CyberForge, DGA detection follows this practical approach. Instead of relying only on a complex external model, the system uses a lightweight heuristic method based on well-known DGA characteristics. These include Shannon entropy, vowel-to-consonant ratio, digit ratio, and patterns in character repetition such as long consonant runs. These signals are combined into a single score that helps determine whether a domain is likely generated by malware.
[271] (BodyText) This approach is intentionally designed to be simple, fast, and reliable. It is also flexible, meaning it can later be replaced or improved with a trained deep-learning model without changing the rest of the system. In this way, CyberForge keeps the balance between strong detection ability and practical deployment in real-time environments where speed and stability are important.
[272] (Heading2) 2.6 Indicator Extraction and Cyber Threat Evidence Representation
[273] (FirstParagraph) Indicators of Compromise (IOCs) come from real cybersecurity practice before they became a topic in academic research. They started as a simple way for security teams to share clear signs of an attack. When an incident happens, analysts need small pieces of evidence that prove something bad is going on. These pieces of evidence are what we call IOCs. They can include things like IP addresses, domain names, URLs, email addresses, file hashes, and sometimes even registry keys or malware signatures.
[274] (BodyText) Over time, as cyber-attacks became more complex, sharing IOCs also became more structured. This led to the creation of standards like STIX and TAXII (Barnum, 2012). These standards made it possible for different security tools and organisations to exchange threat information in a common format. Instead of sending plain-text reports, systems could now send structured data that machines can understand and process automatically. This helped improve speed and coordination between security systems.
[275] (BodyText) In research, different methods have been used to extract IOCs from data. Some methods use natural-language processing, where systems try to understand written reports and pull out useful security information (Liao et al., 2016). Other methods use machine-learning models that are trained to recognise patterns in text and identify possible indicators. More recent work even uses large language models to find security-related information from long documents. These methods are powerful, but they can also be complex, slow, or hard to control in real-time systems.
[276] (BodyText) Because of this, many real-world security tools still rely on simple and direct methods for IOC extraction. One of the most common methods is pattern matching, especially regular expressions. This works by checking text against known patterns that match things like IP addresses, domain names, hashes, or URLs. This method is widely used because it is fast, easy to understand, and gives consistent results.
[277] (BodyText) In CyberForge, IOC extraction is done directly from the content of web pages collected by the system. The extractor looks for several types of indicators. These include IPv4 and IPv6 addresses, domain names, URLs, email addresses, cryptographic hashes such as MD5, SHA-1, and SHA-256, Bitcoin wallet addresses, and CVE identifiers used for known software vulnerabilities.
[278] (BodyText) This approach is chosen because it works well in real-time systems. Cybersecurity systems need to make quick decisions, so speed is very important. Another reason is clarity. When a system flags something as an IOC, a human analyst should be able to easily see why it was flagged. Regular expressions make this possible because the rule is simple and transparent.
[279] (BodyText) The system also uses filtering rules to reduce false alerts. For example, not every domain name found on a page is dangerous. Some domains are well-known safe references or examples used in documentation. The system tries to ignore these safe cases while still capturing real threats. This balance between sensitivity and accuracy is important for reducing unnecessary alerts.
[280] (BodyText) Overall, IOC extraction in CyberForge is designed to be simple, fast, and reliable. It focuses on practical detection rather than complex learning models, because in real security environments, clarity and speed are often more important than complexity.
[281] (Heading2) 2.7 Structured Adversary Behaviour Mapping Using MITRE ATT&CK
[282] (FirstParagraph) The MITRE ATT&CK framework is a globally recognised knowledge base that describes how cyber attackers operate in real-world environments (Strom et al., 2018). It is organised into a set of tactics and techniques that represent different stages of an attack, from initial access to final impact. Each technique has a unique identifier, making it easier for security systems and analysts to communicate using a shared language.
[283] (BodyText) In cybersecurity research, MITRE ATT&CK is widely used for mapping observed system behaviour to known attack patterns. This helps move beyond simple detection and allows systems to explain how an attack is happening, not just whether it is malicious. Because of this, it has become an important tool in both academic research and enterprise security operations.
[284] (BodyText) In CyberForge, MITRE ATT&CK is used as a structured layer for interpreting signals produced by other components in the system. Instead of leaving results as raw observations, the system maps findings such as suspicious form behaviour, unusual script activity, or credential-capture attempts into specific ATT&CK techniques. This makes the output more meaningful and easier for analysts to understand.
[285] (BodyText) The framework also helps in visualising the progression of an attack. By arranging detected techniques according to their position in the attack lifecycle, the system can show how far a threat has progressedfrom initial-access attempts to possible execution or impact stages. This supports faster decision-making and improves situational awareness for users.
[286] (BodyText) In the implementation of CyberForge, a simplified technique catalogue is used, where each detection rule is linked to a MITRE technique and a confidence score. This allows the system to combine rule-based detection with structured adversary knowledge. While more advanced research exists that automatically maps free-text descriptions to the MITRE framework using machine learning, the current approach prioritises clarity, speed, and interpretability. This makes it suitable for real-time browser-based security analysis while still aligning with established industry standards.
[287] (Heading2) 2.8 Multi-Agent Systems and Agent-Based AI in Cybersecurity
[288] (Heading3) 2.8.1 Classical idea of multi-agent systems
[289] (FirstParagraph) Multi-agent systems (MAS) are an old idea in artificial intelligence (Wooldridge, 2009). The main idea is simple: instead of one big system doing everything, you use many smaller systems called agents. Each agent has its own job. It can observe data, make decisions, and take action based on its task (Russell & Norvig, 2020).
[290] (BodyText) In this setup, agents can work together to solve problems that are too big or too complex for one system alone. Some agents cooperate, some coordinate, and in some cases they may even compete depending on the system design. The goal is always the same: break a complex problem into smaller parts so it becomes easier to solve.
[291] (BodyText) In early research, multi-agent systems were used for things like distributed problem solving, simulations, and network monitoring. In cybersecurity, they were also used for intrusion detection. Different agents would monitor different parts of a network and share alerts when something suspicious happened. The idea looked very strong on paper, but in practice it was not widely adopted. One main reason was complexity. When too many agents communicate, the system becomes slow, hard to manage, and difficult to maintain in real-time systems.
[292] (Heading3) 2.8.2 Agentic AI and modern systems
[293] (FirstParagraph) Recently, multi-agent systems have become popular again because of large language models. Instead of using only small rule-based agents, modern systems can now use LLMs as reasoning units that can plan, decide, and interact with tools.
[294] (BodyText) In this new approach, a system can break a task into steps, assign each step to a different agent, and then combine the results at the end. This makes the system more flexible and closer to how humans think when solving problems.
[295] (BodyText) A key idea behind this change is the ReAct framework (Yao et al., 2023). In this approach, an AI system does not only think once and give an answer. Instead, it follows a loop: it reasons, takes action, observes the result, and then reasons again. This cycle continues until a final decision is made. Another related idea is from Generative Agents (Park et al., 2023), where multiple AI agents are given memory and can behave over time in a more realistic and continuous way.
[296] (BodyText) In cybersecurity, this approach is very useful. When a security analyst checks a suspicious URL, the process is not just one step. It is a sequence of actions. The analyst first suspects something is wrong, then checks the URL, then looks at behaviour, then checks threat-intelligence sources, and finally makes a decision.
[297] (BodyText) This same idea is used in CyberForge. Instead of relying on a single model, the system uses multiple agents. Each agent has a specific job, such as classification, scraping, extraction, or threat lookup. A final reporting agent then combines all results and produces a final decision. This makes the system more structured and easier to understand.
[298] (Heading3) 2.8.3 How agents are coordinated
[299] (FirstParagraph) Multi-agent systems can be organised in different ways. Some systems use a simple sequence where one agent runs after another. Others run all agents at the same time. More advanced systems use a graph structure where agents are connected based on their dependencies.
[300] (BodyText) CyberForge uses a directed acyclic graph (DAG). This means agents are arranged in steps, and each step depends on the previous one when needed. This design is chosen because it balances speed and structure.
[301] (BodyText) In CyberForge, some agents do not depend on others. For example, the URL classifier and the DGA detector only need the URL itself. These can run immediately and in parallel with other processes like web scraping. This helps reduce waiting time.
[302] (BodyText) Other agents depend on scraped page data. For example, IOC extraction, behavioural analysis, and MITRE mapping can only start after the web content is collected. Once the scraper finishes, these agents can also run in parallel to save time.
[303] (BodyText) There is also one agent that depends on multiple earlier results. The threat-intelligence agent needs IOCs before it can query external sources like OTX. This makes it a later-stage process in the pipeline.
[304] (BodyText) Finally, all results are sent to a reporting agent. This agent combines everything and produces the final verdict. It decides whether the URL is safe or malicious based on all available evidence.
[305] (BodyText) This DAG structure is simple but effective. It reduces delays, avoids unnecessary computation, and keeps the system organised. It also makes it easier to expand the system later by adding new agents without breaking the existing flow.
[306] (BodyText) Overall, the multi-agent design in CyberForge reflects a shift in modern AI systems. Instead of relying on a single model, intelligence is distributed across many small parts that work together to achieve better results in real-time cybersecurity protection.
[307] (Heading2) 2.9 Large Language Models, Sandboxing, Threat Intelligence, and Cross-Platform Security
[308] (FirstParagraph) This section combines four related ideas from cybersecurity research: large language models (LLMs), sandboxing, threat-intelligence systems, and cross-platform security design. These areas are different, but they all connect to the same goal: helping systems detect threats, explain them clearly, and protect users in real time.
[309] (Heading3) 2.9.1 Large Language Models in security systems
[310] (FirstParagraph) Large language models have changed how many AI systems are built. After the introduction of models like GPT-3 (Brown et al., 2020), it became clear that a single model could perform many tasks such as answering questions, summarising text, and generating explanations without being trained separately for each task. Later research also showed that step-by-step reasoning improves model performance, especially for tasks that need multiple steps of thinking, such as analysis and decision-making (Wei et al., 2022).
[311] (BodyText) Language models generate advisory explanations from supplied context. The current Space defaults to a pretrained Qwen3.5-2B GGUF model through llama.cpp. Backend provider routes and a separate user-key desktop path may also produce answers. Responses must retain their engine attribution; fluent reasoning text is not independent detector evidence or proof of an executed action.
[312] (BodyText) The original prototype used a Gemini-to-Mistral-to-template explanation fallback. Current routing includes the in-Space Qwen model and configured backend or user-key providers. Missing, busy or failed models must be reported honestly, with any rule-based summary identified explicitly. The original provider ordering is retained only as historical experimental context.
[313] (Heading3) 2.9.2 Sandboxing and behavioural analysis in cybersecurity
[314] (FirstParagraph) Sandboxing is a technique used in cybersecurity to safely analyse suspicious files or URLs. The main idea is to run something in a controlled environment and observe what it does. For example, a system can open a file or webpage in isolation and watch its behaviour without risking the real system. Classic sandbox systems like Cuckoo Sandbox and CWSandbox were designed for this type of deep analysis (Willems et al., 2007).
[315] (BodyText) In traditional security systems, sandboxing often means full dynamic execution. This includes running programs inside virtual machines, monitoring system calls, tracking file changes, and observing network traffic (Egele et al., 2012). However, this level of analysis requires heavy infrastructure and is not always practical for lightweight or web-based systems.
[316] (BodyText) In CyberForge, the term “sandbox” is used in a simpler way. It does not execute files or run full virtual machines. Instead, it acts as a structured analysis view where all results from the system are displayed. This includes the final verdict, extracted indicators, MITRE mapping, behavioural signals, and model outputs. It is more of a decision workspace than a full execution sandbox.
[317] (BodyText) This design choice is intentional. Full dynamic analysis requires container systems or virtual machines, which are not part of the current deployment environment. However, the system is designed in a way that it can be extended later. A future version could connect to external sandbox services that perform real execution and send back behavioural results.
[318] (Heading3) 2.9.3 Threat intelligence systems
[319] (FirstParagraph) Threat intelligence refers to the collection and use of information about cyber threats (Tounsi & Rais, 2018). This includes data about malicious domains, IP addresses, attack patterns, and known attacker infrastructure. The goal is to help systems recognise threats faster by using shared knowledge from previous attacks.
[320] (BodyText) Modern threat-intelligence platforms collect data from many sources and make it available through APIs. Some platforms are commercial, while others are community-driven. One widely used free system is AlienVault Open Threat Exchange (OTX), which provides continuously updated threat data contributed by security researchers and organisations around the world.
[321] (BodyText) In CyberForge, the Threat Intelligence agent uses OTX to check extracted indicators such as domains and IP addresses. When an indicator is found, the system queries OTX to see if it has been reported before. If a match is found, the related threat information is added to the final report. This helps improve confidence in the detection and adds external validation to the system’s internal analysis.
[322] (BodyText) OTX is chosen because it is easy to access, has a structured API, and supports automated queries. It also fits well with the system design because it allows real-time lookups without complex setup. In practice, most strong security systems use more than one threat-intelligence source, combining multiple feeds to improve coverage and accuracy.
[323] (Heading3) 2.9.4 Cross-platform security architectures
[324] (FirstParagraph) Modern users do not stay on one device. They move between desktops, laptops, and mobile devices while browsing the web and accessing online services. Because of this, security systems must also work across different platforms and keep information synchronised. This idea is often seen in industry systems known as XDR (Extended Detection and Response).
[325] (BodyText) XDR systems collect data from many sources such as endpoints, networks, cloud services, and email systems. They combine all this information in one place so that security teams can see a full picture of threats, an approach that depends on the same shared-intelligence principles described in the threat-intelligence literature (Tounsi & Rais, 2018). Although XDR is widely used in industry, academic research on it is still developing, especially in terms of small-scale and modular implementations.
[326] (BodyText) The current repository contains a Tauri desktop client and a React Native/Expo companion, alongside a shared-core CLI and a stdio MCP adapter. These interfaces expose different implemented subsets rather than guaranteed feature parity. Native mobile capture and platform release readiness require separate acceptance testing.
[327] (BodyText) MongoDB control-plane records, selected Appwrite integrations, local stores and native authenticated event streaming support persistence and updates. Ownership is derived from verified principals and workspace membership. The current console reports backend, stream and ML states separately instead of equating a successful HTTP response with full protection.
[328] (BodyText) Even though CyberForge focuses only on web-based threats, its architecture follows the same general idea as cross-platform security systems: one central intelligence layer, multiple access points, and continuous synchronisation of security information.
[329] (Heading2) 2.10 Research Gaps
[330] (FirstParagraph) The literature reviewed in this chapter shows strong progress in AI-based cybersecurity, especially in phishing detection, DGA detection, threat intelligence, and multi-agent systems. However, there are still important gaps between research ideas and real working systems. These gaps form the motivation for this study and guide the design of CyberForge.
[331] (BodyText) Gap 1: Lack of full working multi-agent security systems. Many recent AI frameworks such as LangChain, AutoGPT, and similar agent tools show how multi-agent systems can work in theory (Yao et al., 2023). However, very few complete and openly available systems show how these ideas can be applied directly to cybersecurity in a real end-to-end pipeline. Most examples stop at demonstrations or partial workflows. This study fills that gap by building a full working system that connects multiple agents into one complete URL-security-analysis pipeline.
[332] (BodyText) Gap 2: Handling model and service failure. The current implementation exposes versioned capability readiness and unavailable/unknown states, with explicitly attributed fallback text where applicable. This builds on the historical multi-provider explanation design but does not imply that a failed model still produces a verified threat verdict.
[333] (BodyText) Gap 3: Focus on accuracy instead of real false alarms. A lot of existing research focuses on accuracy scores like F1 or precision, but this does not fully reflect real use (Sommer & Paxson, 2010). In practice, what matters more is how often safe websites are wrongly marked as dangerous. This is called false positives. Many systems perform well in lab tests but are not practical because they flag too many safe URLs. CyberForge focuses on reducing false positives by combining multiple signals from different agents and using a final decision rule that balances average confidence and strongest evidence. This makes the system more usable in real browsing situations.
[334] (BodyText) Gap 4: Reusing historical context. Memory can supply prior observations and reduce repeated work (Park et al., 2023). In CyberForge this is retrieval and caching, not online weight learning. Whether historical context improves detection quality requires a controlled comparison; it cannot be inferred merely from the existence of a memory store.
[335] (BodyText) Gap 5: Difficulty in reproducing research systems. A large amount of cybersecurity research is not easy to reproduce because it depends on private datasets, closed systems, or expensive infrastructure. This makes it hard for other researchers or students to build on the work. CyberForge is designed using publicly accessible tools and platforms so that it can be reproduced and extended more easily. The system is built to run in a modular way so that different parts can be tested or improved independently.
[336] (BodyText) These gaps show that there is still a need for cybersecurity systems that are not only accurate, but also practical, explainable, memory-aware, and easy to deploy. The next chapter explains how CyberForge is designed and implemented to address these challenges through a full multi-agent architecture.

[383] (BodyText) The use-case diagram illustrates how different users and system components interact within the CyberForge platform. The main purpose of the diagram is to show the activities that take place when a user browses a website and the system automatically analyses that website to determine whether it is safe or potentially harmful. The diagram also shows how different services work together to generate a final security report and alert the user when threats are detected.
[384] (BodyText) The primary actor is an authenticated user who may submit an address manually or enable supported collection. The user separately controls reading history, observing active tabs, sending addresses to the backend, LLM processing and synchronisation.
[385] (BodyText) The desktop is a Tauri 2 application with Rust commands and a static HTML/CSS/JavaScript renderer. Supported browser observations depend on OS capability and privacy settings. The renderer displays actual native/backend responses rather than assuming a scan or protective action succeeded.
[386] (BodyText) For the specialist analysis route, an accepted URL is dispatched to the retained orchestrator. For the versioned URL-analysis route used by the shared CLI/MCP operation, the backend requests a checked ML analysis record. These paths are related but do not have identical aggregation or execution semantics.
[387] (BodyText) The first group of agents starts by examining the URL itself. The URL Classifier checks whether the structure of the URL resembles known malicious or phishing websites. At the same time, the DGA Detector checks whether the domain appears to have been generated automatically by malware. Another agent, known as the Web Scraper, collects information from the webpage, including page content, network activity, response headers, and other technical details. The Memory Reader simultaneously searches historical records to determine whether the same website has been visited before and whether previous visits produced suspicious results.
[388] (BodyText) After the first stage is completed, the second stage begins. The collected webpage information is passed to another group of agents. The IOC Extractor searches the page for indicators of compromise such as suspicious domains, IP addresses, email addresses, file hashes, cryptocurrency wallets, and known vulnerability identifiers. At the same time, the Behavioural Analyser examines how the webpage behaves by looking for suspicious scripts, unusual network requests, hidden forms, dangerous JavaScript functions, or other activities commonly associated with malicious websites. The MITRE Mapper then compares the discovered evidence against known attacker techniques documented in the MITRE ATT&CK framework. This helps the system understand how an attacker may be operating and what stage of an attack is being observed.
[389] (BodyText) Once these analyses are complete, the system moves to the third stage. The Threat Intelligence Agent takes the extracted indicators and checks them against external threat-intelligence sources. In CyberForge, this process is performed using AlienVault OTX. If any indicator is already known to be associated with malicious activity, the information is added to the report and contributes to the overall threat score.
[390] (BodyText) The retained Reporter combines available specialist findings into a risk score and evidence report. Its score policy is not interchangeable with the newer trained_models_v1 analysis policy. Consumers must retain the originating policy and treat missing coverage as missing evidence.
[391] (BodyText) Where enabled and available, an attributed language model turns supplied findings into advisory text. A failure or template response is labelled accordingly. No language-model explanation proves that a detector ran or an operating-system action was applied.
[392] (BodyText) Persisted findings and memory provide context for later requests. This reuse does not modify model weights; current detector retraining is a separate owner-authorised offline procedure. Data retention and synchronisation follow the applicable account scope and privacy controls.
[393] (BodyText) The client presents the reported verdict, evidence and limitations. Supported protective actions are requested explicitly or proposed through the agent workflow, approved where required, and evaluated through actual receipts. The system does not guarantee it can prevent interaction with every page before content loads.
[394] (BodyText) The use-case diagram therefore demonstrates the complete workflow of CyberForge, from the moment a user visits a website to the moment a final threat assessment is delivered. It highlights how multiple AI agents, memory services, threat-intelligence feeds, and reporting mechanisms work together to provide real-time protection and help users browse the web more safely.

[399] (BodyText) Analysis begins with a manually submitted URL or an observation permitted by the user. Browser-history and foreground observation are platform-dependent, so complete capture of all browsing is not assumed.
[400] (BodyText) Native commands validate privacy choices and use the authenticated backend session. Sensitive address components are redacted before transmission. If required consent or capability is absent, the request reports that limitation.
[401] (BodyText) The backend derives account/workspace scope from authentication and selects the requested service. Cached observations may reduce repeated work where the configured path supports them, but freshness and model provenance must remain visible.
[402] (BodyText) A cached result is historical evidence and must be identified as such. The original experiment reported repeat responses below 100 ms; this source revision does not remeasure cache latency or assert that every client uses the same cache.
[403] (BodyText) An allow-list or popularity reference must not force an unexamined URL to be classified clean. Current design distinguishes domain popularity features, user exceptions and security verdicts. Hosted phishing can occur on a popular platform, so allow-list membership is not proof of safety.
[404] (BodyText) The selected analysis path runs only its supported components. The retained three-stage specialist DAG and the newer versioned detector-analysis endpoint are distinct; a CLI URL scan does not implicitly execute the entire page-scraping DAG.
[405] (BodyText) Within the specialist DAG, Stage 1 includes the BERT URL classifier, DGA heuristic, Web Scraper and Memory Reader. The first two consume the address/domain; the others collect content and prior context. Stage 1 tasks can run concurrently.
[406] (BodyText) Alongside these two components, the Web Scraper collects information directly from the webpage. It retrieves the page content, HTML structure, response headers, scripts, and other useful information. This data is important because many threats cannot be detected by examining the URL alone. Some malicious behaviour only becomes visible after the page content has been inspected.
[407] (BodyText) Once these first-stage analyses are completed, the system waits until the web-scraping process has finished. This is necessary because several later agents depend on the information collected from the webpage. After the scraping results become available, the second stage of analysis begins.
[408] (BodyText) During the second stage, the IOC Extractor examines the collected page content and searches for indicators of compromise. These indicators may include suspicious IP addresses, domain names, URLs, email addresses, file hashes, cryptocurrency wallet addresses, and other artefacts that are commonly linked to cyber threats.
[409] (BodyText) Behavioural rules inspect the page signals returned by the scraper, such as scripts, forms, redirects and network metadata. They do not establish arbitrary browser execution, full-system malware detonation or a trained network-intrusion detector.
[410] (BodyText) Another component running during this stage is the MITRE TTP Mapper. This module compares the findings against techniques documented in the MITRE ATT&CK framework. By doing this, the system can understand whether the observed behaviour resembles known attacker techniques. This provides additional context and helps explain how a threat operates.
[411] (BodyText) After the IOC extraction, behavioural analysis, and MITRE mapping processes are completed, the findings are sent to the AlienVault OTX enrichment stage. Here, CyberForge checks extracted indicators against global threat-intelligence databases. If any indicator is already known to be associated with malicious activity, the system adds this information to the report. This external validation helps improve confidence in the final verdict.
[412] (BodyText) The current ReportAgent uses a weighted evidence sum: URL score (30%), DGA contribution (10%), rendered-page evidence (35%), behavioural contributions, reputation/IOC/ATT&CK additions and a domain-history multiplier, capped at 100. Separately, the versioned trained_models_v1 endpoint reports threat if an answering trained detector flags, benign if answering trained detectors agree on benign, and unknown when no trained detector answers. Heuristic outputs remain contextual estimates. These policies require independent evaluation and must not be conflated.
[413] (BodyText) A verdict is interpreted with the named policy, detector coverage and uncertainty. Scores are not presented as calibrated probabilities. A service responding successfully does not imply that every model is ready.
[414] (BodyText) A benign result is an assessment under the available evidence, not a guarantee of safety. Unknown, missing-coverage and failed states remain explicit. Retention of the result is subject to the relevant store and consent policy.
[415] (BodyText) A threat result can trigger a displayed warning and, in supported workflows, an action proposal. Approval, queueing, delivery and application remain distinct states. A queued command is never recorded as an applied block merely because the server accepted it.
[416] (BodyText) When permitted, the explanation path produces attributed advisory text. The current default Space model is Qwen; Gemini and Mistral observations in Chapter 4 belong to the original experiment. An explanation does not independently validate the threat or perform remediation.
[417] (BodyText) Supported records are written to their designated account/workspace stores. Local memory and optional caches retain context where configured. Consent withdrawal prevents further restricted collection or sharing; retention and deletion controls must be assessed separately.
[418] (BodyText) The revised flow makes the boundaries of collection, inference, evidence, consent and action visible. It preserves the original modular research design while avoiding claims of universal capture, unconditional safety, guaranteed model availability or autonomous remediation.

[479] (Heading3) 3.7.2 Calibration of the Risk-Score Formula
[480] (FirstParagraph) The original risk-score calibration used seven researcher-labelled URLs (Appendix A), removed the +0.5 offset and adjusted thresholds. This is a small development calibration exercise, not held-out evidence of generalisation. The current feature-based trainer instead separates domains for fitting, threshold selection and evaluation and records model-specific thresholds; historical and current aggregation paths remain different policies.
[481] (Heading3) 3.7.3 Calibration of the DGA Heuristic
[482] (FirstParagraph) The original DGA calibration used 30 legitimate and generated-looking labels with an empirical 0.45 threshold. The current DGA endpoint still uses explicit entropy and character-pattern heuristics rather than a fitted sequence model. Its reported score or confidence must not be interpreted as calibrated maliciousness probability. A larger held-out DGA corpus remains necessary.
[483] (Heading3) 3.7.4 Verification of the LLM Fallback Chain
[484] (FirstParagraph) The original prototype exercised Gemini exhaustion, Mistral fallback and a rule-based final response. These are historical verification observations. Current tests must instead exercise the actual configured Qwen/backend/user-key paths, busy/time-budget behaviour and unavailable states, while checking engine attribution and preventing advisory text from being labelled as executed work.
[485] (Heading2) 3.8 The Eight-Agent Analysis Pipeline
[486] (FirstParagraph) The retained specialist pipeline has eight analysers plus a final Reporter. It analyses accepted inputs rather than guaranteeing analysis of every browser event. Its decomposition supports complementary evidence; an ablation study would be needed to quantify improvement over a single-model baseline.
[487] (BodyText) The agents are organised into three stages. Stage One focuses on analysing the URL and collecting information about the target website. Stage Two examines the collected content and searches for signs of malicious activity. Stage Three enriches the findings using external threat-intelligence sources. After all agents complete their tasks, the Reporter Agent combines the results into a final threat assessment and generates a report for the user.
[488] (BodyText) Table 3.1 presents the complete eight-agent pipeline used in CyberForge.
[489] (tbl) Stage Agent Input Main Function Output Stage 1 URL Classifier URL Analyses the URL using machine learning to determine whether it is legitimate or malicious. Label, confidence score, threat score Stage 1 DGA Detector Domain name Checks whether the domain appears to have been generated automatically by malware using Domain Generation Algorithms (DGAs). DGA score, features, verdict Stage 1 Web Scraper URL Collects page content, network requests, response headers, forms, scripts, and browser-related information. Scraped website data Stage 1 Memory Reader Domain name Searches previous scan records and browsing history to determine whether the domain has been analysed before. Visit history, previous verdicts, risk trends Stage 2 IOC Extractor Scraped content Searches for indicators of compromise such as suspicious domains, IP addresses, URLs, hashes, email addresses, and CVE identifiers. List of extracted IOCs Stage 2 Behavioural Analyser Network traffic, scripts, headers Detects suspicious behaviours such as credential collection, hidden redirects, dangerous scripts, suspicious API calls, and abnormal browser activity. Behaviour findings and severity levels Stage 2 MITRE Mapper Scraped content and behaviour findings Maps detected activities to relevant MITRE ATT&CK tactics and techniques. MITRE techniques and confidence levels Stage 3 Threat Intelligence Agent Extracted IOCs Queries external threat-intelligence services to determine whether detected indicators have been reported previously. [490] (TableCaption) Table 3.1: The CyberForge eight-agent analysis pipeline
[491] (BodyText) Pipeline operation. When a user visits a website, the URL is first sent to the Agent Orchestrator. The orchestrator creates a scan session and launches the four Stage One agents simultaneously. Running these agents in parallel helps reduce waiting time and allows the system to collect different forms of evidence at the same time.
[492] (BodyText) The URL Classifier determines whether the URL resembles known phishing or malicious URLs. The DGA Detector examines the structure of the domain name to identify patterns commonly associated with malware-generated domains. At the same time, the Web Scraper retrieves information from the website, while the Memory Reader checks whether the domain has previously appeared in the user’s browsing history.
[493] (BodyText) After Stage One is completed, the collected website content becomes available to the Stage Two agents. The IOC Extractor searches the page for known security indicators, the Behavioural Analyser investigates how the website behaves, and the MITRE Mapper translates suspicious findings into recognised attacker techniques using the MITRE ATT&CK framework.
[494] (BodyText) Once these analyses are completed, the Threat Intelligence Agent begins Stage Three. This agent uses the extracted indicators to perform reputation checks against external threat-intelligence sources. If an indicator has been linked to previous attacks or malicious campaigns, the information is added to the analysis.
[495] (BodyText) Finally, the Reporter Agent receives the results from all previous agents. It combines the findings, calculates the overall risk score, determines the threat level, generates a human-readable explanation, stores the report in the database, updates the memory system, and sends the final result back to the user interface.
[496] (BodyText) This pipeline integrates complementary evidence into an inspectable report. The current versioned detector endpoint and fixed-template durable agent framework coexist with it and have narrower, explicit contracts. Neither memory retrieval nor fixed tool sequences establishes online learning or unconstrained autonomous planning.
[497] (Heading2) 3.9 Evaluation Methodology
[498] (FirstParagraph) The system is evaluated in Chapter 4 against four criteria:
[499] (p) Functional correctness. Each of the eight agents must return the documented response shape on a representative input, and the Reporter must produce a verdict matching the curated expectations on the calibration URL set.
[500] (p) False-positive rate. On a corpus of common benign URLs (google.com, github.com, wikipedia.org, bbc.co.uk, stackoverflow.com, arxiv.org), the system must produce a verdict of clean or low-risk in 100 % of cases.
[501] (p) True-positive coverage. On a corpus of curated phishing URLs (drawn from PhishTank and from manual construction), the system must produce a verdict of suspicious or malicious in at least 80 % of cases.
[502] (p) End-to-end latency. The mean pipeline duration measured across one hundred consecutive requests must not exceed ten seconds under cold-start conditions and four seconds under warm conditions.
[503] (FirstParagraph) Chapter 4 retains the original measurements. The supplied thesis does not include a complete raw per-URL result log, a reproducible split manifest or a controlled single-model ablation. Consequently, the revision does not claim to reproduce those measurements or establish statistical superiority. Source-contract tests of current features are evidence of implementation behaviour, not replacement detection experiments.

[588] (Heading1) Chapter FiveCONCLUSION, RECOMMENDATIONS AND PERSPECTIVES
[589] (Heading2) 5.1 Conclusion
[590] (FirstParagraph) This dissertation presents the design and historical evaluation of CyberForge and a source-grounded revision of its current implementation. Eight specialist analyses and reporting provide the research architecture; later work adds Tauri/Rust clients, authenticated workspace control, durable agent/device workflows, a private ML service and limited CLI/MCP integration. These implementation changes do not retroactively change the original experimental baseline.
[591] (BodyText) The original experiment reports 284 correct classifications among 300 URLs, with 137 harmful URLs detected, 13 missed and three benign URLs falsely flagged. Mean latency was 4.05 seconds. These results motivate further study of an integrated, explainable workflow but do not prove superiority to a single model, universal protection or current production performance.
[592] (BodyText) The current source implements many controls recommended after the original prototype, including verified identity/workspace checks, independent privacy choices, service authentication, device signing and explicit action states. Remaining work is to demonstrate those controls in packaged releases and live services, evaluate detector quality on independent data and close the feature gaps identified in Appendix C.
[593] (Heading2) 5.2 Recommendations
[594] (FirstParagraph) Based on the development process, the testing phases, and the subsequent gap analysis, the following recommendations are proposed for the future enhancement of the system:
[595] (p) Security assurance. Extend verification of existing session, workspace, per-window native permissions, service credentials and signed-device-command controls. Exercise account switching, grant revocation, hostile input, replay protection, expiry and UAC denial/approval in the packaged product; source existence alone is not enterprise assurance.
[596] (p) Privacy and retention. Validate the five existing consent categories, URL redaction, local-store deletion/retention and synchronisation withdrawal across clients. Audit all external recipients, including MCP clients, rather than proposing consent and redaction as wholly absent features.
[597] (p) Model quality and training. Expand temporal/domain-held-out evaluation, measure false positives on legitimate login and shared-hosting sites, and isolate training from inference with durable jobs and controlled model promotion. User feedback should enter a reviewed labelled dataset; automatic online retraining is not currently implemented and should not ingest untrusted feedback unchecked.
[598] (p) Action and integration scope. Extend the supported, approved device-action workflow with verified rollback before enabling broader guarded automatic response. Complete the planned AI CLI and MCP operation families only when their permission, evidence, cancellation and recovery contracts are implemented. Current queued/delivered receipts must remain distinct from applied outcomes.
[599] (Heading2) 5.3 Perspectives
[600] (FirstParagraph) Future research should run longer deployments with raw measurement logs, compare agent ablations, test current models on independent regional and hosted-phishing corpora, and evaluate explanation quality with a defined blinded protocol. Product work includes isolated training, richer grounded AI CLI operations, broader MCP transports/tools, packaged mobile/native-capture acceptance and optional integration with a genuine dynamic-execution sandbox. The existing companion and limited stdio MCP/CLI source should not be described as either wholly absent or fully complete.

[642] (Heading2) C.3 ML components and types of learning
[643] (FirstParagraph) Supervised learning: phishing_detection, malware_detection and web_attack_detection use HistGradientBoostingClassifier on labelled URL examples or URL-carried SQL-injection/XSS payloads. These are not binary-file malware detectors or a universal network intrusion detector. Unsupervised learning: anomaly_detection uses IsolationForest fitted to benign URL features; anomaly is not proof of maliciousness.
[644] (FirstParagraph) Transfer/pretrained inference: BERT URL classification uses an externally trained artefact; Qwen3.5-2B GGUF generates advisory text through llama.cpp. Neither is fine-tuned by the current trainer. DGA is an entropy/character-pattern heuristic, IOC extraction uses rules, and memory is retrieval/context. No reinforcement learning or automatic online weight updates are established by the active source.
[645] (FirstParagraph) Source: ml-services/hf_space_deploy/app.py, trainer.py and url_features.py. Current dependencies pin scikit-learn 1.8.0 for stored artefact compatibility and llama-cpp-python 0.3.36. The canonical service is FastAPI REST without Gradio; per-capability readiness is separate from HTTP reachability. Owner training uses a different authority from ordinary inference credentials.
[646] (Heading2) C.4 Training phases and evaluation
[647] (FirstParagraph) Phase 1 — collect and clean. Download task-specific public corpora, normalise and deduplicate addresses, build the popularity reference and exclude external-reference test URLs from fitting. Capture source metadata and settings. Source datasets are listed in Section 3.6.5 and trainer.py.
[648] (FirstParagraph) Phase 2 — features and partitions. Use the same url_features.py definitions in training and serving. Group by registered domain; GroupShuffleSplit reserves a default 20% test partition and a further 10% of the training partition for threshold selection. The estimator also uses its own internal early-stopping validation; this should not be confused with the external domain-held-out test.
[649] (FirstParagraph) Phase 3 — fit. Fit the three supervised HistGradientBoostingClassifier models (defaults: up to 300 iterations, learning rate 0.1, 31 leaves, seed 42) and a benign-only IsolationForest (200 trees, default contamination 0.02). These are configurable defaults in source, not a new training-run report.
[650] (FirstParagraph) Phase 4 — choose thresholds and evaluate. Select supervised decision points against a default 2% false-positive target on the threshold-selection set; assess held-out data, fixed legitimate/hostile cases and external reference samples where applicable. Record features, metrics, threshold, warnings and accepted/rejected status. Threshold rescaling is not probability calibration.
[651] (FirstParagraph) Phase 5 — publish accepted artefacts. Upload only accepted models with their metadata through the owner-authorised training path and load the available artefacts for inference. The current training job runs in a background thread in the serving process; independent durable workers, immutable whole-bundle promotion and robust rollback require further work. No training run or deployment was performed for this revision.
